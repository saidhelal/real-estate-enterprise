# Governance change-request interception

Privileged destructive/financial mutations do NOT execute directly. They are intercepted, parked as a `change_request` (pending), and only run after an Owner / Super Admin approves.

## Backend mechanism
- ONE global Express middleware (not a per-entity registry) intercepts every `DELETE` matching the bare-resource shape `^/api/[a-z-]+/[^/]+$` and protected `PATCH` on a fixed list (contracts, installment plans/schedules/collections, receipts, journal-entries, customer/supplier-invoices, payment-vouchers, cheques). Nested sub-action routes (e.g. `/cheques/:id/transition`) are intentionally NOT intercepted — they stay direct.
- On intercept it creates a pending `change_request` capturing method/path/payload/reason and returns **HTTP 202** `{ pendingApproval: true, requestId, request }` — the original handler never ran.
- On **approve**, the change-requests route re-dispatches the original request internally to `127.0.0.1:$PORT` carrying a boot-generated bypass-secret header. The middleware honors the secret and lets it through, so ALL existing handlers + side-effects (GL posting, unit recompute, etc.) are reused with zero duplication. Status flows pending → approved → executed (or failed with executionError).
- Approval is gated by `approvals.approve` permission (or `"*"`). Owner & Super Admin are seeded with `["*"]` + `isSystem`.

## Requester authorization (do NOT remove)
- The governance middleware runs BEFORE the route's own `requirePermission`, so it must authorize the requester itself: it derives the required permission as `${camelModule}.${action}` (kebab path segment → camelCase, DELETE→delete, PATCH→update) and rejects with 403 unless the user has it or `"*"`.
- **Why:** without this, any authenticated user could park a delete/edit change request for an entity they cannot mutate, and an approver could unknowingly execute it (IDOR). Caught in code review.

## Reason requirement
- The change reason is supplied via the `x-change-reason` header (optional `x-change-entity-label`). It is MANDATORY: middleware returns 400 on empty/whitespace reason; the ResourceManager delete dialog disables submit until a reason is entered.

## Scope enforcement (status)
- `user_scopes` (branch/dept/project) is modeled, assigned via the Users UI, and loaded into AuthUser, but runtime query filtering by scope is NOT yet wired across business modules (no shared query layer). Treat comprehensive scope enforcement as a separate cross-cutting feature, not as already-done.

## Frontend cooperation
- `setNextChangeReason(reason, entityLabel?)` (exported from `@workspace/api-client-react`, in `custom-fetch.ts`) sets those headers on the **next** DELETE/PATCH/PUT only, consumed once.
- Any create/update/delete `onSuccess` must detect `result.pendingApproval === true` and toast `governance.submitted` instead of the normal created/deleted toast — a 202 is success, not completion. `ResourceManager` and the Users page both do this.

## Force-password-change
- `users.mustChangePassword` flag: admin reset sets it true; `change-password` clears it.
- Enforced on BOTH layers: server-side `requireAuth` blocks a flagged user from every authenticated route except `/auth/me`, `/auth/change-password`, `/auth/logout` (403 `{mustChangePassword:true}`) — this is the real control. The web AuthProvider redirect to `/change-password` is convenience; that page invalidates the current-user query on success so the gate releases.
- **Why server-side matters:** a client-only gate is bypassable via curl/devtools. A flagged user with a valid access cookie could otherwise call privileged APIs. Caught in code review.

**Why:** central interception means new destructive endpoints are governed automatically without wiring each one; internal re-dispatch avoids re-implementing side-effects. **How to apply:** to exempt or add a protected route, edit the middleware's path matcher / protected-PATCH list — do not add per-entity approval code in handlers.
